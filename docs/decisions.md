### Статус SMS-провайдерів (D15)

| Провайдер | Статус | Примітка |
|---|---|---|
| TurboSMS | Адаптер написано, **потребує перевірки** | Endpoint `api.turbosms.ua/message/send.json` з офіційної документації. Назви полів тіла запиту, спосіб передачі токена і коди відповіді ще треба перевірити на тестовому акаунті |
| SMSClub | Заплановано | Відомий endpoint `im.smsclub.mobi/sms/send`. Авторизацію і поля не перевірено |
| AlphaSMS | Заплановано | Є публічна JSON-документація API v1.5. Не реалізовано |

Інші провайдери додаються так: новий файл у `packages/sms/src/providers.ts`, запис у `SMS_PROVIDER_CATALOG` зі статусом `available`, тести з підміненим `fetch`.

## Відкриті питання (потребують рішення)

1. **Вхід клієнта без SMS.** Варіант за замовчуванням: вхід через Google, Meta або Telegram; телефон обов'язковий (D13) і підтверджується адміністратором дзвінком. Потрібно підтвердити.
   Зауваження: вхід за телефоном через OTP у Supabase потребує SMS-провайдера, який Supabase підтримує напряму. Для TurboSMS це треба перевірити окремо, бо OTP-інтеграція може бути недоступна.
2. **Доступ майстрів до даних клієнта з іншого салону.** Це міжтенантний доступ до персональних даних. Потрібна юридична оцінка і згода клієнта. Поле `clientDataSharingBetweenSalons` у налаштуваннях зарезервовано, але без юридичного висновку не вмикати.
3. **Instagram.** Потрібна App Review і бізнес-верифікація Meta. Для запуску відкладено.
4. **Утримання передоплати.** Юридична перевірка до запуску. У коді це налаштовувана політика.
5. **Скидання пароля співробітника через Telegram.** Потрібен окремий флоу поверх Supabase Auth. Не реалізовано.
6. **Вартість і тип оплати власного домену.** Не визначено, у схемі лише поле `custom_domain`.
7. **Блокування входу клієнтів.** Не блокуємо за специфікацією, у схемі не передбачено.

## Не реалізовано на Етапі 0

- Row Level Security у Supabase (буде окремою міграцією разом з Етапом 1).
- Логіка розрахунку слотів (Етап 2).
- Автентифікація і екрани (Етап 1).
- Telegram-бот, нагадування, платежі.
